# Web Architecture

The [product design](superpowers/specs/2026-10-11-sudoku-design.md) and [variants design](superpowers/specs/2026-10-11-sudoku-variants-design.md) define behavior, [AGENTS.md](../AGENTS.md) defines development conventions, and [README](../README.md) lists setup and verification commands. This document describes current module ownership. See [Adding a Sudoku Variant](variant-extension.md) for the concrete extension checklist.

## Organization

The frontend adopts the explicit application composition and cohesive feature organization reviewed in the local `sctv-dl` project. Sudoku retains its pure engine, computation workers, transactional persistence, and editing ownership as independent layers. Create responsibility directories only for code that exists; free play, daily challenges, and full-board practice stay in the game workflow.

```text
src/
  main.ts
  runtime.ts
  App.vue
  layouts/AppLayout.vue
  router/index.ts
  theme/useTheme.ts
  shared/components/
  shared/model/boardGeometry.ts
  shared/utils/keyboardOwnership.ts
  features/
    home/views/
    game/{views,components,composables,model,stores}/
    learning/{views,composables,model,stores}/
    records/{views,components,model,stores}/
    settings/{model,stores}/
  core/sudoku/
  storage/
  worker/
  styles/
```

| `router/`                    | Existing routes and their views; static-host hash navigation                                                             |
| `theme/useTheme.ts`          | One composable for light/dark/system synchronization and Naive UI configuration from the shared CSS palette              |
| `shared/components/`         | Controlled SudokuBoard, NumberPad, and ConfirmationDialog; emit actions without choosing a store or persistence strategy |
| `features/home/views/`       | Workflow entry dialogs and a standalone resume action, with a saved-session chooser when needed                          |
| `features/game/views/`       | GameView for free play/full-board practice, DailyView for challenges                                                     |
| `features/game/components/`  | Controlled setup/settings dialogs, session controls, and logical hint presentation                                       |
| `features/game/composables/` | Route entry, keyboard ownership, lifecycle listeners, save triggers, and route-leave behavior                            |
| `features/game/model/`       | Pure session transitions, clock calculations, daily policy, and display helpers                                          |
| `features/game/stores/`      | Player session actions composed with internal persistence and transition owners                                          |
| `features/learning/`         | Lesson models/examples, progress store, exercise composable, and views; practice composes GameView                       |
| `features/records/`          | Aggregation, records store, history view, and confirmed local-data controls                                              |

## Dependency Direction

- Application composition connects layouts, themes, and features with storage and workers through `runtime.ts`. Feature stores and composables access its injected services. Business and browser-service modules never import App, main, router, layouts, or theme implementation.
- Shared components depend on Vue, Naive UI, shared components, and pure engine types/helpers. They never import features, storage, workers, or the application runtime. Shared means reusable across Sudoku workflows, not generic to every application.
- Views render store state and call actions; they never open the database or call the repository directly. Learning may compose the game view, and home may read game/records models and stores.
- Game, learning, and settings models remain pure and consume engine or other pure model exports. Records aggregation consumes game models and a persisted result type; that type-only storage dependency performs no I/O.
- Storage, workers, and the application runtime may consume pure feature models, never feature stores, components, or views. Storage and workers never import the application runtime. Storage owns persisted-data validation and editing leases; `storage/database.ts` owns their shared connection-provider type. Runtime injection is a Vue browser adapter outside the pure engine.
- The engine imports only engine modules and has no framework, UI, database, or browser-global dependencies.

ESLint enforces these boundaries for static imports and dynamic `import()` using the same policy. Dynamic imports use string-literal module paths so their dependencies can be checked. The Node-environment suite in `tests/module-boundaries.test.ts` exercises rejected and permitted imports with the real lint configuration. Tests may import composition and cross-feature fixtures to verify complete behavior.

## Imports and Naming

Use `@/` for imports into `src/`, including local modules. Vite resolves an absolute source directory; the shared TypeScript configuration supplies the same mapping for application, worker, and test checking. Fixtures outside `src/` retain relative imports.

The worker deliberately keeps `new Worker(new URL('./sudoku.worker.ts', import.meta.url), { type: 'module' })`. Source aliases do not replace asset URLs. See the [Vite alias reference](https://vite.dev/config/shared-options.html#resolve-alias), [Vite worker guidance](https://vite.dev/guide/features.html#web-workers), and [TypeScript paths reference](https://www.typescriptlang.org/tsconfig/paths.html).

Views use PascalCase `*View.vue` names; components use descriptive PascalCase names, composables `use...`, and stores `use...Store`. Tests stay beside their owners. The board test lives beside SudokuBoard even though fixtures use session data. Avoid barrel exports or empty directories solely for symmetry.

RecordsView uses validated type queries for its desktop sidebar and compact mobile selector. Its media-query listener mounts only the active navigation surface and disposes with the view; switching layouts also closes an open selector. Type changes scroll to the top, while browser history restores the saved position. Lesson digit input and game shortcuts share the UI ownership guard under `shared/utils/`; lesson keys call the same exercise answer action as touch buttons and yield while full-board practice owns the route. Recovery and practice links compose RouterLink custom slots with Naive UI anchor buttons, preserving normal link and modified-click behavior.

## Runtime Contracts

The entry provides one runtime. `useGameEntry` and `useDailyEntry` own route initialization, target lookups, and entry cleanup; views retain presentation and confirmations. `useLessonExercise` owns temporary exercise state, shared keyboard actions, and delayed-answer fencing. `GameSettingsDialog` is a controlled view of preferences and policy slots. The game store retains clock, input, hints, and completion; `sessionPersistence` owns attached queues, revisions, dirty state, and idempotent lease release, while `sessionTransitions` owns save-before-switch coordination and one cancellation generation. Their factories do not import the store that composes them. App settles/leaves the game before runtime disposal. Route-owned listeners, timers, and worker jobs retain existing cleanup. Layout extraction adds no KeepAlive or route transitions.

GameControls renders a compact common-action row and a Naive UI More menu. Its typed events reach the existing GameView session actions; the view owns settings and confirmation modals, and DailyView owns choosing another challenge. Menu attributes expose visible ownership to the shared keyboard handler; closed-menu transitions do not block board input. The installed dropdown's built-in keyboard mode only changes highlights, so public option attributes provide real DOM focus and navigation following the [WAI menu-button pattern](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/). Selecting a modal action first focuses the stable More trigger so cancellation can restore focus. NumberPad accepts an optional row layout for full-board touch play and lesson exercises. Shared keyboard ownership guards keep game and lesson shortcuts outside composite controls and open dialogs. Native media queries show game digits for narrow or coarse-pointer devices without JavaScript device guessing; coarse-pointer and short desktop layouts retain a usable board width. DailyView composes an entry overview or the active board, with detailed policy in settings rather than repeated above the board. Read-only daily saves still allow opening the independent challenge chooser; existing store transitions determine whether a switch can proceed. Home promotes records to a fourth card and both resume actions use the same shared palette through Naive UI's Info button theme.

Keyboard, touch, and hints reach the same game actions. Existing routes accept a validated `variant` query; explicit saved-session links restore the stored type. Ordinary free/daily entry waits for the player to open a setup dialog. Home confirms choices before navigating, passing transient `start=1` intent and a validated free-play `difficulty`; successful transitions replace those parameters with the actual type/session identity so refreshing resumes instead of generating again. Dialog selections stay local and do not mutate a running puzzle. Home and game/daily views compose the same controlled `GameSetupDialog`, while each owner handles starting, saved-session lookup, and errors through existing stores. Successful free/practice transitions synchronize the actual type/session query without restoring the already active session. A save-before-install guard pauses and flushes the active session before generation, restoration, or daily switching; an ordinary write failure retains the current in-memory session and editing rights for retry. Revision or ownership conflicts make the session read-only. A separate, explicitly confirmed reload action replaces local edits only after reading the latest record; failed recovery leaves local edits intact.

AppLayout renders the common parent link: workflow pages return home, lessons return to their own type's course path, and full-board practice returns to its own lesson. Typed route metadata resolves lesson destinations at the composition boundary, following the [Vue Router route metadata convention](https://router.vuejs.org/guide/advanced/meta.html), so the layout does not import lesson data. These destinations are deterministic for direct links as well as in-app navigation. LearningView derives the selected course from the validated `variant` query, completion from the learning store, and its recommended unfinished lesson from the current-lesson preference. It keeps all lessons accessible without changing progress identifiers or persistence. The router scrolls to the top when entering a different page, choosing a different learning type, or switching a lesson between its exercise and full-board practice. Browser back/forward restores the saved position, following the [Vue Router scroll behavior contract](https://router.vuejs.org/guide/advanced/scroll-behavior.html). Session-query updates preserve the current board position. Modal body dimensions are passed to Naive UI directly because its teleported preset surface does not retain the calling component's scoped-style attribute.

`PuzzleRules` is a discriminated union under `core/sudoku/ruleTypes.ts`, re-exported through the public `rules.ts` facade. `variantRegistry.ts` composes typed decoders/compilers from `variants/*.ts`; topology helpers live in `ruleTopology.ts`. Definitions never import their registry. Its compiled `RuleContext` distinguishes complete nine-digit units, duplicate peers, related highlights, and arithmetic/path constraints. Jigsaw replaces boxes; Killer cages and Arrow shafts are not nine-digit units. Framework-independent bounded evaluation drives candidates, conflicts, uniqueness, completion, and explainable deductions. Clue reductions appear as typed evidence rather than hidden candidate pruning. Exhaustion remains inconclusive.

`features/game/model/variants.ts` owns the complete Chinese catalogue and ordered choices. `shared/model/boardGeometry.ts` composes typed board adapters to format actual regions and clues without solving. Engine definitions contain no framework or presentation dependencies. `SudokuClues` draws decorative SVG in board coordinates, while the CSS Grid retains buttons, notes, digits, and focus. Accessible cell labels and selected-rule text explain the geometry; pause removes clue presentation as well as values.

Session construction captures the dataset epoch before Worker computation and retains it through fresh lease acquisition and atomic creation. A peer's restored epoch cannot authorize an older operation, even when BroadcastChannel notification is absent or delayed. Daily eligibility reads carry the same pre-computation fence. Learning exposes dataset/reset readiness generations so a mounted lesson clears old answers and resumes restored cursors after reload, while ordinary completion writes retain explicit Next interaction and imported last-visited preferences remain intact.

Preferences merge initial updates into the committed settings base rather than persisting unread defaults. A dataset conflict blocks further writes until canonical settings are reloaded; retry does not attach an old snapshot to a new epoch. Lesson cursor writes carry the learning dataset epoch, and exercise readiness waits for recovered preferences and progress. This protects imported cursors even without prompt reset broadcasting.

`GenerationInput` pairs each type with its current generation version. `generation.ts` owns request/limit decoding, current identities and metrics. `generationSearch.ts` owns one request budget, at most two active layouts and their bounded candidate frontiers. `generationCandidates.ts` owns 81-bit clue masks, novelty and deterministic removal/restoration/exchange cursors; these masks are internal and never persisted or sent through the Worker. Lower-tier solved checkpoints and target-stalled checkpoints occupy separate shares of eight slots per layout, borrowing unused capacity. Layout creation is counted before terminal/geometry work, including failed attempts. At 40 attempts, active frontiers may continue without creating another layout. A solved removal lineage keeps one existing checkpoint slot while its ordinary sweep continues, because human difficulty tiers are not monotonic under clue removal. Closed proposal allowances release their slots without forgetting seen masks. Already eligible layouts receive turns according to actual charged work; continuing progress does not trigger a fixed-work preemption quantum.

`generationLayouts.ts` statically assembles constructors for all six variants, keeping construction imports separate from the pure geometry registry to avoid a dependency cycle. `generationStrategies.ts` and variant modules declare legal geometry and digit/complement transforms. `classicGeneration.ts` retains the Classic terminal adapter; `variantGeneration.ts` owns focused geometry construction/transforms and rule necessity. `terminalConstruction.ts` owns bounded complete-unit construction, including Jigsaw's shuffled unit prefill and 6,561-visit per-attempt cap. Arithmetic clues are built afresh for the new terminal. Authored examples serve grading/teaching and region presets, never replacement-puzzle delivery.

Every delivery passes one acceptance path: validated identity/rules/terminal-consistent givens, exact requested tier and Classic clue policy, complete assessment, completed exact count of one matching the terminal, then variant necessity with the existing Jigsaw exception. A known terminal proves existence rather than uniqueness. A stalled checkpoint has unknown uniqueness unless independently counted, and cannot authorize delivery. New version-owned terminal/geometry/candidate random substreams keep unsuccessful clue exploration from changing later terminals. There is one current production dispatcher, no historical generator, fallback source or hidden retry allowance.

`search.ts` is the exact-count boundary. A layout's prepared validator and standalone counting use the same `propagationSearch.ts` implementation. Immutable cell-to-unit and cell-to-constraint memberships are compiled with the owned rule context. Each probe initializes fresh givens/domains, then trails changes and restores to a branch mark on every exit, including exhaustion. Propagation queues stay branch-local; returned solutions own their arrays. Only full nine-digit units require each digit; duplicate peers and arithmetic clues remain distinct. Exact-search guesses never supply logical evidence.

`constraintSupport.ts` owns raw exact support and prepared arithmetic catalogues. Killer cages of size at most four use complete ordered tuples from distinct sum combinations, capped at 512 tuples per constraint and 8,192 per layout. Capacity overflow discards partial preparation and falls back to bounded enumeration without refund; larger cages, Arrow and Thermo retain exact enumeration. Incomplete preparation/filtering is inconclusive. `constraints.ts` uses the same support for candidates/conflicts, and logical combination deductions use it with one complete local-domain memo per cage in each fresh workspace. Static catalogues may cross candidate boards within their layout; domain-dependent support cannot.

Storage writes format-2 sessions/results and normalizes validated format-1 records to Classic without rewriting historical facts. The database schema stays at version 1. Free replacement is transactional and scoped by type, learning retains one practice slot, and leases/revisions/dataset epochs continue to fence stale writes. Formal daily identities and eligibility are independent by type/date; Classic IDs remain compatible. Pure aggregation produces six daily statuses and six separate record summaries.

`storage/backup.ts` owns format-1 local backups, preflight bounds, complete collection decoding, readonly export snapshots and atomic replacement. The repository supplies its connection and committed reset notification. `useRecordsStore` settles game/preferences before export/restore, owns preview epochs and recovery feedback, and reloads settings/progress/catalogues after current or peer replacement. `LocalBackupPanel` owns file selection/download and confirmation presentation. Game's `prepareBackup` action reuses save-before-transition ordering and cancellation. Imported revisions start at 1; leases are cleared and the local dataset epoch advances. Stored facts and the database schema remain unchanged. See [Local Backup](local-backup.md).

`core/sudoku/ratingPolicies.ts` owns explicit per-type ordered policies and `sudoku-rating-v2`; `rating.ts` owns bounded assessment, successful-trace summaries, and runtime decoders. Standalone assessment creates its own budget; `assessPuzzleWithBudget` consumes a validated caller-owned budget without resetting it. `logic.ts` charges each detector pass for every type and can resume a caller-owned logical workspace. Rating reuses candidate state and prior deductions only when the next policy's actual priority order preserves the earlier prefix, including Classic's canonical ordering. Otherwise it resets both state and trace from the original board. Prior deductions count toward the total per-policy step limit, and the complete successful trace retains the existing summary semantics. No workspace crosses assessment requests. Each workspace owns at most one complete exact support snapshot per cage. `variantTechniques.ts` checks context identity, geometry, sum and effective domains before reuse; every constraint visit is charged before lookup, and incomplete enumeration is never cached. Raw support enumeration and exact search do not use this memo. The prepared `screen` operation returns a classification with an owned completion callback; `assess` immediately completes it for standalone callers. Completion produces the full successful-trace statistics without another policy search or charged work. There are no legacy rating wrappers. Neither grading nor statistics substitute for uniqueness validation.

`prepareAssessmentWithComputation` borrows a layout's already charged immutable rule/support computation. Ordinary `prepareAssessment` validates and owns its inputs, then performs charged preparation lazily inside evaluation. Each board gets fresh logical state and domain memo. `screenTarget` distinguishes below-target, matching-target, target-stalled, invalid and work/step exhaustion, stopping at the requested policy. Full `assess`/`screen` continue through supported policies using the same runner. Only actual policy-priority prefixes may continue; changed priorities reset state and trace, and prior steps count toward each policy's total limit. Trial completion replays the owned trace and returns independent evidence/summary data without another policy search or synthetic work. Rating remains `sudoku-rating-v2`.

Prepared data is scoped to its owner, with no cross-request search cache. Caller rule edits and returned evidence/solution edits cannot corrupt later probes. Replacing a layout retires its computation and frontier together; scheduling preserves useful active checkpoints while a progressing layout continues its sweep.

Production `worker/sudoku.worker.ts` adapts the engine's current generation/assessment contracts. Generation delivery reuses the accepted assessment summary. Worker domain outcomes remain separate from transport cancellation, timeout, and failure. The engine imports no browser/storage adapters. Daily and free construction use the same current factory without date-cutover routing, while stored formal attempts retain precedence. Tests exercise real emitted workers at both deployment roots against authored fixtures and explicit expected outcomes.

Generation defaults are 40 layouts, four million shared construction work units and 500 steps. `GenerationLimits` has exactly those three fields; `GenerationMetrics` reports construction work, attempted/completed layouts, candidate visits and exclusive preparation/arithmetic/exact/logic/proposal work. Stage work sums to total work, including abandoned and inconclusive operations. Engine exhaustion causes distinguish work, logical steps, layout creation and exhausted frontiers; Worker envelopes retain their existing public status/message. Diagnostic timing belongs to the harness, never deterministic search choices. An exhausted construction returns no puzzle or assessment. Standalone assessment defaults to four million work units. The client owns at most one prepared idle module Worker in addition to isolated active jobs; idle startup computes no puzzle, retains startup errors, and is cleaned up on disposal. Actual generation requests have a three-second timeout, while assessment and hints retain fifteen seconds. Timeout publishes no alternative puzzle. Game views render one cancellable live generation notice, preserve paused-board concealment and retain the current save on interruption. Deterministic exhaustion reports a Chinese error and asks for a new selection, while timeout and transport failures retain identical-input retry. See [Generation Without Fallback](superpowers/verification/2026-10-14-generation-without-fallback.md).

`GameSession.assessment` is an optional compact snapshot. `sessionTransitions.ts` installs it in the same fenced replacement transaction as the puzzle and preserves it on free restart. Storage decodes it only after validating the base session; absence stays absent and corrupt, unsupported, or mismatched metadata becomes explicit unavailability. Restoring sessions/results never requests assessment or changes original difficulty. Existing format-2 records and database schema 1 need no migration.

Root and `/sudoku/` builds must load real worker assets. Browser tests exercise every new type at both roots, and independent test oracles validate returned puzzles without calling production compilation or search. Chromium desktop/mobile emulation and WebKit are configured alongside Firefox; host launch failures and physical-device verification are reported separately.

## Advanced play and course contracts

`core/sudoku/difficulties.ts` statically covers all six types and 19 supported type/tier combinations. Expert belongs only to Classic and must be rejected for variants at generation, transport, persistence, and player selection boundaries. Easy/Medium/Hard technique policies remain unchanged. `advancedTechniques.ts` owns bounded advanced detection and direct proof validation; unit, candidate, fish, wing, and strong-link premises cannot be supplied by a search answer or manual player notes.

Learning owns 32 stable IDs, authored candidate snapshots in `courseFragments.ts`, and ordered exercise/transfer states in `exerciseStages.ts`. Every unit requires two exercises; combined variant units use three stages per exercise. Stage cursors use optional settings metadata and dataset epoch fencing. Only committed final completion writes enter lesson progress. Preserve all original lesson completion IDs and the independent lifetime of full-board practice.
