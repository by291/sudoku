# Algorithm references and design rationale

These primary sources provide background for the maintained algorithms. Source links explain an idea or an alternative; they do not imply that the repository embeds that implementation. The current Rust code and the linked topic documents define shipped behavior.

## Constraint propagation and exact solving

| Reference                                                                       | Useful material                                                                                | Relationship to this project                                                                                                                               |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Peter Norvig, [Solving Every Sudoku Puzzle](https://www.norvig.com/sudoku.html) | Constraint propagation followed by search, including choosing a cell with few remaining values | Background for the approach in [exact search](constraints-and-search.md); the Rust implementation adds variant support, bounded work and trail restoration |
| Donald E. Knuth, [Dancing Links](https://arxiv.org/abs/cs/0011047)              | Reversible sparse structures for Algorithm X exact-cover search                                | An alternative studied during solver research; production uses domain propagation and MRV rather than DLX                                                  |

Classic Sudoku has a natural exact-cover formulation: each candidate assignment `(row, column, digit)` covers cell occupancy, row-digit, column-digit and box-digit requirements. Arithmetic/path variants need additional modeling. The current shared support layer directly expresses these constraints and shares them with conflicts, deduction evidence and exact counting.

DLX and general-purpose SAT/CSP solvers remain alternatives, not runtime dependencies. Historical experiments do not establish a current performance ranking. Replacing the backend would still need explicit cancellation/work limits, owned results, uniqueness semantics and compatibility with the variant model.

| ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Radek Pelánek, [Difficulty Rating of Sudoku Puzzles: An Overview and Evaluation](https://www.fi.muni.cz/~xpelanek/publications/sudoku-arxiv.pdf) | Evaluation against human solving data; both individual step complexity and dependencies matter | Explains why a technique label or raw search cost is not a validated player-time estimate; this project does not implement or claim validation by that study's model |

The teaching material is separately authored and validated against explicit candidate states. External examples should not replace the independent evidence validators or become expected test outputs generated by the implementation under test.

## Generation and targeted difficulty

| Reference                                                                                                                                          | Useful material                                                                             | Relationship to this project                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Kohei Nishikawa and Takahisa Toda, [Exact Method for Generating Strategy-Solvable Sudoku Clues](https://arxiv.org/abs/2005.14098)                  | A constraint-satisfaction formulation for generating clues solvable by specified strategies | Research context for targeting a reasoning repertoire; the current generator evaluates nearby clue masks instead of implementing the paper's exact formulation |
| Tdoku, [Generating Puzzles](https://github.com/t-dillon/tdoku#generating-puzzles)                                                                  | Candidate pools, clue changes and configurable generation objectives                        | Relevant to feedback-guided exploration; this project has its own bounded frontier and exact logical-tier acceptance                                           |
| KDE KSudoku, [cagegenerator.cpp](https://raw.githubusercontent.com/KDE/ksudoku/master/src/generator/cagegenerator.cpp)                             | Cage growth from tight corners and absorption of cells that would otherwise become isolated | Reference for the Killer growth heuristic; KDE's solver, operators and complete generator are not the project's implementation                                 |
| Simon Tatham's Solo, [source in the maintained Android port](https://raw.githubusercontent.com/chrisboyle/sgtpuzzles/main/app/src/main/jni/solo.c) | Integrated Sudoku solving and generation, including irregular regions                       | Historical reference for regional construction; the current prefill, branching and local limits are defined by the Rust constructor, not this upstream file    |

The retained design is terminal construction followed by bounded clue-mask exploration, with separate logical and exact checks. Some earlier experiments explored other backends or cage-geometry changes. They are not shipped algorithms and their temporary results are not maintained here.

## How to use these sources

Read the relevant topic alongside its source owners before changing an algorithm. In particular, distinguish mathematical validity, local support, logical solvability, unique solvability and empirical player difficulty. Evidence for one is not automatically evidence for another.

When incorporating a new idea, document its actual implemented scope and limits. Preserve seeded ordering, work accounting and independent proof/fixture contracts, or explicitly version the change. Keep durable explanations here; keep executable examples and regression coverage with the owning tests.
